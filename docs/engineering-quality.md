# Soulflow Agent 开发质量规范

领取 Soulflow 工单的开发者和编码 Agent 用本页确定交付证据。开工前先写一个可以观察的验收条件，提交拉取请求（PR）前运行质量检查。另一位维护者根据工单、代码差异和持续集成（CI）结果决定是否接受变更。

## 为工单写验收条件

新功能从一个真实场景开始。负责人写明使用者、输入、预期结果、范围和至少一个会改变判断的反例。影响行为的未知项由提议人确认，结论记回工单。跨模块功能沿用仓库的需求规划流程，依次关联自然语言原文、结构化需求、PRD、开发计划和可独立验收的工单；上游版本变化时复查受影响工单。小修复可直接在 Issue 写复现步骤和正确结果。限时探索在工单记录要验证的假设、观察和去留决定，进入主干前补齐相应行为验证。[GitHub Spec Kit](https://github.com/github/spec-kit)

例如，用户要求「把两个 Agent 的决策请求放到同一页」。可验收的行为是成员在同页看到两个待答问题，回答 A 后，只有 A 的原会话收到回复。反例是两个会话恰好使用相同请求编号。先明确谁有权回答、重复提交会得到什么结果，再把展示、回复路由和审计拆成可验证的工单。这里描述的是产品验收示例。

## 用测试约束关键行为

修复缺陷和开发确定性业务规则时，先写一个能从公开入口失败的测试，确认失败原因符合预期。用最小实现让它通过，再在测试保护下重构。断言使用者可观察的状态、返回值或副作用。复用已有测试覆盖的小改动，记录对应测试即可。界面探索可先用可点击原型确认交互，再为保留的关键流程补浏览器验证。[Martin Fowler 对 TDD 的说明](https://martinfowler.com/bliki/TestDrivenDevelopment.html)

| 变化 | 合入前应看到的证据 |
| --- | --- |
| 工单依赖或验收映射 | 用固定输入验证合法计划、缺失引用和循环依赖。 |
| 外部 Agent 或工具适配器 | 对脱敏协议样本做契约测试，覆盖未知消息、断线或重复事件；涉及真实接入的结论另附实际交互证据。 |
| 权限、决策路由、审计 | 从应用入口验证越权拒绝、相同请求编号的会话隔离和重复提交；核对审计记录可追踪结果且没有凭据。 |
| 自然语言生成 PRD 与工单 | 保留脱敏输入及人工确认的验收要点。用固定样本比较规则通过率、验收项遗漏和人工修订；模型生成、工单结构校验和人的批准分别留证。 |

## 评审注释和模块边界

源码、测试和工程配置中的说明性注释使用中文。优先记录接手的人仅凭代码难以判断的设计原因、业务约束或边界条件。标识符、版本号和工具指令保留原写法。例如在工单依赖校验中，注释应说明为什么剩余工单也可能只是受循环阻塞，避免维护者把它们全部标记为环上的成员。

按业务能力组织模块。权限与状态变更由拥有该状态的模块处理，外部 SDK、网络和存储放在各自边界。领域代码仅引入当前用例实际需要的接口。新增抽象时，评审者应能指出它隔离的外部变化、消除的重复，或保护的业务约束。拆单按用户可验收的行为切分；清理无关代码另开变更。[Google 代码评审指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

## 在本地运行 PR 质量检查

在仓库根目录使用 Node 22.17.1，运行以下命令。第一条按锁文件安装开发工具，第二条依次执行严格类型检查、静态检查和行为测试。当前规划模块由 Node 直接运行 TypeScript。引入需要打包的客户端或服务时，在同一检查入口加入真实构建。

```sh
npm ci --ignore-scripts
npm run check
```

**预期结果。** 命令以状态码 0 退出，类型检查与静态检查通过，测试报告显示失败数为 0。若检查中断，先查看第一个失败环节。在仓库根目录单独运行对应的 `npm run typecheck`、`npm run lint` 或 `npm test` 定位问题，修复后再运行完整检查。

PR 写清哪条验收条件由哪个测试或演示覆盖，注明剩余风险。另一位维护者审阅完整差异，重点看模块职责、失败路径、向后兼容和测试能否捕获错误。涉及产品或权限决策时链接对应版本的人工答复。CI 记录关联本次提交；最新差异通过检查并获独立人工批准后，按贡献指南合入。[GitHub 关于 Agent 使用与局限的说明](https://docs.github.com/en/copilot/responsible-use/agents)

## 撰写技术文档

先写一句话说明谁在什么场景下会打开本页，以及读完后能完成什么。用读者要做的事命名标题。新术语在首次出现时解释，命令、字段和错误信息保留可搜索的原文。[Google 技术写作课程：识别读者](https://developers.google.com/tech-writing/one/audience)

按读者的问题选择写法。同一主题可以相互链接，篇幅由任务决定。[Diátaxis 文档框架](https://diataxis.fr/)

| 读者的问题 | 适合的写法 | Soulflow 示例 |
| --- | --- | --- |
| 第一次使用，从哪里开始？ | 教程，用一个能跑通的小例子带读者完成首次操作。 | 用一份示例计划运行拆单测试。 |
| 我怎样完成眼前的任务？ | 操作指南，写清前置条件、步骤、成功标志和常见失败的处理办法。 | 在本地运行 PR 质量检查。 |
| 某个字段或错误是什么意思？ | 参考文档，按稳定名称列出定义、取值、约束和例子。 | 查找工单的 `dependsOn` 字段。 |
| 为什么这样设计？ | 设计说明，记录背景、选择、代价和重新评估的条件。 | 解释为何由应用层负责批准工单。 |

写操作步骤时，按实际执行顺序写，每步说明一个动作。把运行位置、版本或权限放在命令之前，把可观察的成功结果放在命令之后。提交前按正文运行示例。写尚在设计中的功能时标明状态和预期结果，已有验证则链接到对应版本的证据。[Google 开发者文档风格指南：操作步骤](https://developers.google.com/style/procedures)

## 发布到飞书「开发文档」

行为契约、数据结构与运行命令随代码在同一个 PR 更新。维护者将有明确来源、适用范围、版本和复核证据的工程文档，通过飞书 CLI 发布为 Soulflow 知识库中的原生云文档。研究参考可凭一手来源和可复现结果发布，标注验证环境与评审状态；标记为团队生效规范时须关联采纳记录。讨论、未验假设和原始会话留在各自受控工作区。[Write the Docs 的文档即代码指南](https://www.writethedocs.org/guide/docs-as-code/)

1. 在 Soulflow 知识库查找「开发文档」。首次发布且目录缺失时，在空间根部创建同名父节点。
2. 查找已有文档。首次发布时用 `lark-cli docs +create` 指定父节点；已有原页放错目录时用 `lark-cli wiki +move` 移动原节点。更新前回读当前修订，与上次发布内容比对，保留协作者的修改。
3. 写入后用 `lark-cli docs +fetch` 核对标题、正文、示例和来源链接，用 `lark-cli wiki +node-list` 确认原页出现在「开发文档」下。
4. 在内部发布记录中保存来源提交或内容摘要、飞书链接、修订号和验证日期。团队可在飞书提出修订，行为契约的修改回到仓库评审。
