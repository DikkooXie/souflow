# souflow 长期开发方案

**路线图 · 2026 年 11 月 28 日**

## 产品定位

**souflow 是能统筹公司工作、亲自执行并交付结果的企业超级员工。** 它统一管理项目、工单、人员、Agent 和执行设备。负责人给出企业目标和授权，souflow 把目标变成可验收的工作，按需要组织人和 AI 一起完成，核对结果，再把经验带到下一轮。

对负责人来说，打开首页就能知道公司在推进什么、哪里遇到阻塞、哪些事需要拍板。想看细节，可以追到工单、原话、提交、测试和实际回执。想交代新工作，可以直接跟 souflow 讨论。它会主动补充证据、指出问题、提出方案，并在获准的范围内把事情办完。

长期价值要在真实工作中证明。先看质量和业务结果，再看负责人花了多少时间协调、返工了几次、多少工作能在既有授权下完成，最后看交付耗时和模型用量。公司每完成一类工作，就多积累一份下次能直接使用的能力和证据。

## 开发顺序

每个阶段交付一个当期能用的结果，并在下一阶段选一张真实工单验证复用效果。排期以验收条件、真实需求和可用资源为依据。已经明确的范围先落实，后续业务选实际样本后再细化。

| 阶段 | 交付 | 验收 | 给下一阶段复用 |
| --- | --- | --- | --- |
| **1. 首版开发闭环** | 把一句开发需求变成澄清、版本化计划、真实 GitHub 工单和可交付的 PR。工作台能看派发、设备、审计和验收证据。 | 收尾 #67。两台实体 Mac 使用本机 Codex，在独立工作区并行执行上游工单。上游合并后，下游只唤醒一次，完成测试和关联 PR。同一提交分别复核实现与测试质量、原始需求与验收兑现。保留运行记录和截图。 | 工单、依赖、执行位、授权、独立评审、CI 和真实交付证据。 |
| **2. 持续排期与交付** | 持续同步 Issue 和 PR，统筹多个项目，按真实依赖和设备可用性派发。授权范围内，指定仓库的 PR 通过当前提交的 CI 与独立评审后可自动合并。 | 一条开发链等待上游时，已授权的独立任务能利用空闲执行位。上游解阻后，下游只回到队列一次。工作台能解释等待、改排、派发和合并。 | 有版本和结果的运行样本，包括排期理由、通信回执、人工介入、失败与返工。 |
| **3. 技术发现、科研与知识库** | 定期发现论文、开源项目、Skill、工作流和模型更新。用真实工单回放验证候选，把结论、反例、出处和适用范围沉淀下来。 | 用同一仓库版本、验收条件和可比资源对照两种做法。能重跑实验，并区分原论文能否复现、方法在 souflow 上是否真有收益。下一张同类工单能引用已验证的经验。 | 可重跑的实验、可追溯的知识和能用于下一次规划的证据。 |
| **4. 自动进化** | 把实测有效的小改进变成工单，由 souflow 自己排期、实现、验证、开 PR 并跟踪试用。需要扩大适用范围、权限或改变验收门槛时，由 souflow 提方案，人审批。 | 跑通一次从发现到上线再到效果复验的闭环。能追溯使用中的策略来自哪次实验和哪次变更，并验证出现明确回归时可以恢复到仍符合当前条件的已验证版本。 | 改进流程本身可以复用到办公功能，用真实使用结果继续优化。 |
| **5. 会议决定到交付** | 先从一场真实飞书会议读取纪要，在 souflow 内确认、生成待办、派发和跟进，最后把结果或链接回填飞书。 | 从一条会中明确决定追到待办、执行与最终回执。会中仍有分歧的事项转为待决策。同一个决定只派发一次。 | 来源引用、决定确认、任务派发与回填，供原生会议和群聊共用。 |
| **6. 原生群聊与会议** | 在 souflow 内完成讨论、开会和审批。souflow 主动发现决定、补充证据、提出可行方案，确认后推进执行。 | 群聊里验证它能发现未点名的决定、提出有证据的异议，并追到实际交付。会议里验证参与和记录状态可见、主持人可暂停、关键问题及时提醒，会末能核对决定和待办。 | 自有沟通入口以及从讨论到决策、再到执行和复盘的完整记录。 |
| **7. 扩展到其他办公事务** | 按实际任务扩展客服、行政、情报、法务、税务和专利申请跟踪。客服与行政可以共用受理和跟进，情报与技术发现可以共用监测与验证，专业事务可以共用材料版本、期限、授权与回执。 | 每次用一个真实场景验证完整交付。扩展到第二个场景时，核对共用能力能否减少交接，并维持各自业务规则、权限和验收条件。 | 把验证过的执行能力用于公司其他项目和工作类型，随业务需要继续扩展。 |

**收工复盘安排在后续独立开发。** 用户说「今天结束开发」后，souflow 用当天工单、差异和测试证据，请用户按费曼学习法用自己的话讲清解决了什么、现在如何运作、出了问题去哪里查。复盘未完成的内容留在个人待办，后台已授权的处理照常推进。

## 企业如何分配责任和权限

| 范围 | 默认规则 |
| --- | --- |
| **经营目标与排期** | 企业长期目标由负责人确认。souflow 自主统筹全部项目的优先级、资源和依赖。重大事故时可以保存工作进度并暂停受影响的任务。改变企业方向时，提交数据、取舍和建议供人决定。 |
| **按任务授权** | 每项任务有明确的负责人、执行范围和验收条件。souflow 在既有授权内为子任务分配所需的最小权限，保留授权来源，完成后收回。历史记录用于推荐，拍板依据任务上的正式授权。 |
| **人和 AI 协作** | 区分已派发和已接手，同一项交付保留一个负责人。遇到重复开工，先保留进度，核对归属并交接诊断、补丁和测试。Agent 有分歧时以验收条件和可复现证据收口，证据不足时挂起争议并推进其他任务。 |
| **工作流审批** | souflow 提方案，负责人批准后自动复用。执行顺序、并行方式和模型在授权内自行调整并留痕。适用范围、权限或验收门槛变化时重新审批。批准绑定具体内容、对象和影响，执行前再核对。 |
| **外部执行** | 自动操作使用 souflow 专用身份，关联发起人、授权人、执行设备及评审。对外承诺、订阅和专业顾问按各自的预先授权处理。遇到撤权，立即停止受影响的后续动作，已发出的动作先回读结果。 |
| **负责人工作台** | 首页先看全公司的待决策、关键交付、跨项目阻塞和优先级变化。紧急事项立即通知，普通审批集中在「待决策」，常规进度和结果进定期摘要。核心界面入口或高频路径变化，先提供可操作预览。 |

任务状态由可核对的来源支撑。PR 是否合并，以 GitHub 为准。任务是否通过验收，以 souflow 为准。飞书同步相关结果并附来源。多步任务部分成功时保留已确认的结果，回读不确定步骤后再补做。同一问题反复卡在同一个地方时，保存进度、挂起工单并释放执行位。重大故障由 souflow 先暂停受影响的写入，修复复测后由负责人确认恢复。

常规开发可以用同一模型的独立会话评审，结论绑定到实际审过的提交。涉及授权、数据迁移或高影响操作时，补做针对性验证，必要时换模型或请有权限的人复核。执行顺序和模型选择依据实际交付质量、用量与返工记录持续优化。

交付完成与效果验证分开。通过工单验收就收尾，后续工作可以继续。有明确业务目标时，souflow 开工前选效果指标，尽量记录改动前的基线，并在交付后用实际数据回查效果。

## 技术积累怎样变成下一次的能力

1. **发现。** 从真实任务的阻塞、返工和人工修改记录出发，结合 SendOS 等成熟产品、GitHub 项目、论文和工具更新，写清候选方法能解决哪个具体问题。
2. **验证。** 科研服从开发优先级，用实际余量做实验。新工具和 Skill 可在获准的隔离环境中用合成样例或脱敏数据试跑。记录版本、步骤、成本与运行结果。
3. **沉淀。** 单次结果先标为观察。复验确认质量达标、确实减少介入或返工后，在已授权范围内自动复用。日常重点采集与任务有关的修改意见、前后截图、最终差异和验收结果。完整对话及原始日志留在来源处。可共享的经验注明出处、访问范围和适用条件。
4. **执行。** 证据明确的小改进可以自行建单、派发、交付，再通过真实工单回查。模型、工具或项目结构发生实质变化时，仅将受影响的经验标为待复验。出现明确回归时自动退回符合当前条件的已验证版本，并把原因和证据告知负责人。找不到可用版本时，暂停受影响的流程并提交待决策。

例如，一种列表布局在实际使用中减少了查找待办的时间，新页面和正在修改的页面就优先复用。稳定页面遇到同类问题时，再单独排改进工单，用真实操作和前后截图核对效果。

## 架构与运行原则

- **当前采用 TypeScript 模块化单体。** 项目、任务、调度、授权、审批、证据和知识保持清楚的职责边界。GitHub、Codex 和飞书通过实际交付所需的接口接入。DeepSeek Harness 留作设计参考，插件机制等有明确复用或替换需求后再评估。
- **长期由负责人控制的常开主机运行工作台和调度，Mac 按需接入执行代码。** 设备报告可用性。设备离线时工单继续排队。主机恢复后补查遗漏事件并回读未确认动作。先验证单机恢复，自动切换由真实业务的停机要求决定。
- **新办公场景先用已有工具完成真实工作。** 稳定做法沉淀为工作流。人工交接、返工反复出现，或现有工具达不到验收条件时，再投资自研能力。飞书第一版的办公接入范围为读取会议纪要和回填结果，审批和日常沟通以 souflow 为主。

一期做成的标志是 souflow 能完成自己的真实开发任务。之后每投资一个模块，都拿下一项实际工作检验它带来的收益。企业方向由人确定，souflow 对授权范围内的执行、结果与复盘负责。 [仓库长期计划原则](https://github.com/DikkooXie/souflow/blob/40c4493b5f7c7723b0107cee9858b8089e19461d/docs/requirements-workflow.md#编排长期开发计划)
