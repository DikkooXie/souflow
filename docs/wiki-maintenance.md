# Soulflow 的 LLM Wiki 维护规则

两位成员和各自的 Agent 共用这份规则。采用 Karpathy 的三个层次，保留来源，维护相互链接的知识页，用明确规则指导录入、查询和检查。接口与行为规范随实现评审，知识页解释背景并引用对应版本。

## 存储和受众

| 内容 | 放置位置和处理方式 |
| --- | --- |
| 原始证据 | 公共来源引用稳定 URL、版本或提交；必要且有权留存时保存不可改写的版本快照。私有原件保留在有适当权限的资料库。修订产生新版本并保留旧版来源。 |
| 可公开的知识页 | 主仓库的 `docs/wiki/` 是审阅源。每页一个稳定的英文文件名，页内可用中文。合并并获授权后将对应页面发布到独立的 GitHub Wiki。 |
| 企业内部知识 | 需要双方访问控制的资料使用单独的私有仓库或受限知识空间，可复用相同的索引、来源、日志结构。公开仓库的工作分支、Issue、PR、Wiki 均只接收可公开材料。敏感标题、内部链接、未授权第三方代码、飞书私聊和原始执行日志也属于受限材料。 |
| 业务审计 | 需求、尝试、权限审批和产物由产品的审计存储保留。Wiki Log 只记录知识页的演变。 |

## Obsidian 项目库结构

| 层 | 职责 |
| --- | --- |
| 原始资料 | `inbox/` 暂存待处理材料。经核对且允许本地留存的原件按固定版本存入 `.raw/captured/`，记录来源和 SHA-256。新版本另存。已核对的线上证据可保留稳定链接与修订号。 |
| 知识页 | `wiki/entities/` 存项目等实体入口，`wiki/concepts/` 存可持续维护的专题，`wiki/sources/` 存来源摘要与证据位置。实体页提供现状和专题入口。结论在专题中维护，专题与来源互相链接。 |
| 维护规则 | `wiki/schema.md` 记录本库的录入、查询和质检约定。索引 `wiki/index.md` 按主题和来源导航，`wiki/overview.md` 汇总现状，`wiki/hot.md` 保留近期入口，`wiki/log.md` 从末尾追加维护记录。 |

写入前从索引查找已有结论，优先更新对应专题和来源。核对原件哈希、库内链接、索引覆盖及现状与历史的边界。迁移有引用的章节时保留原锚点跳转，或同步修正入链。写入后如本机有库检查器，运行严格检查并回读索引和受影响页面。

项目仓库记录可共享的规则和工程知识。Obsidian 的私有原件、来源账本、本机路径及内部链接留在获授权的存储位置。

## 每次交付的文档收尾

1. **Obsidian 项目知识库。** 使用仓库配置的本地项目库。优先增补已有主题页，写清做了什么、为何采用、如何验证、适用范围和待办。引用工单、PR、测试结果或可访问的来源。同步索引，按状态变化更新总览，维护近期入口并追加日志。合并前记为待合并，合并后补上经核对的主干提交。
2. **仓库文档。** 在同一 PR 更新受影响的设计、接口、配置、运行说明或验收文档。产生可复用且可公开的项目知识时，更新 `docs/wiki/` 的对应页面、索引和日志。只更新本次变化涉及的内容。
3. **飞书云文档。** 确认合并后，在 Soulflow 知识库「开发文档」或对应产品原页更新团队需要的已核证结论，附 PR、主干提交和验收证据。发布前核对现有内容和编辑权限，优先增补原页。发布后回读，核对新增内容、链接和修订号，再在 Obsidian 记录发布结果。确有必要时，同步更新首版路线与验收方案中的进展和待验证项。

交付汇报逐项列出三处的状态和对应页面或证据。尚未合并时，飞书标记为待合并后同步。因权限或缺少资料无法完成时，写明具体卡点。无需更新时，写明该处文档未受本次变更影响的原因。首次公开发布和扩大访问范围仍按[审阅和发布](#审阅和发布)执行。

## 三个操作

1. **录入（ingest）**：先核对来源权属、可见范围、版本和相关性。从 Home 搜索已有页，优先增补已有结论。每条可争议结论紧邻来源，标明适用条件。已采纳决策引用批准记录；提案标记“待定”。新来源与旧结论冲突时同时列出依据和待核实点。更新受影响的交叉链接、Home 和 Log；同一版本重复录入且无实质变化时结束。
2. **查询（query）**：从 Home 进入最相关的页面，必要时回到原文、合并提交或实际验证。答复给出页面和来源，明确已验证行为、拟议设计和未知项。普通问答按只读处理；可复用的新结论作为独立的录入变更。
3. **检查（lint）**：每次知识 PR 检查变更页面和相邻页：链接能否定位、Home 能否到达、引文是否支持结论、是否过期或互相矛盾、目标受众是否有权阅读。重复的概念页合并时修正引用；旧结论标明被哪次决定替代。把实质修订记录到 Log。

来源页至少包含来源链接、作者或维护方、所读版本或查阅日期、可核查的提要。主题页写明问题、结论、证据和适用范围。Home 为每页保留一句用途；Log 按时间追加，记录动作、受影响页面和依据。两位 Agent 可以分头起草；合并前基于最新主干整合索引和日志，保留双方条目。

## 审阅和发布

团队内部已核证的资料，通过飞书 CLI 发布到 Soulflow 知识库中的原生云文档。采纳状态、版本、证据和回读步骤见[工程质量规范](engineering-quality.md)。受限资料的索引和飞书链接只保存在内部空间。

主仓库的代码审查不会自动保护独立的 `.wiki.git`。知识变更在主仓库走同一套 PR 和独立人工审阅。首版采用手动发布，不引入同步服务。

1. 首次启用时，由获授权的维护者用 GitHub 的 Wiki 标签页创建首个 Home 页面并核查编辑权限。此动作会对仓库读者公开页面。
2. 发布时，在主仓库之外克隆或更新 Wiki 工作副本，查看其默认分支、最新提交和网页端改动；从主仓库**已审阅合并的提交**取出本次涉及的 Markdown 页面，按原文件名放到 Wiki 根目录。原文引用等共享证据优先使用完整 URL。
3. 核对两边差异。发现独立编辑时先合并回审阅源；删除或重命名单独审阅，不做整目录覆盖或强推。发布提交记录来源主仓库 SHA，推送后读取远端版本并核对 Home 和变更页面。在原 PR 或发布记录关联 Wiki SHA。回退通过恢复已审阅的版本并留下新记录完成。
