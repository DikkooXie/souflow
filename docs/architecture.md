# 原型的模块与审计设计

## 模块与所有权

采用 TypeScript 模块化单体。工作台通过应用服务调用业务模块；适配器在启动入口显式装配。目录随功能落地，首版无需动态发现、插件市场或独立微服务。

| 模块 | 拥有的状态和决策 |
| --- | --- |
| 需求与计划 | 原始需求、追问、回答、计划版本、验收条件、成员确认记录。改版生成新版本，指出受影响工单。 |
| 工单与交付 | 工单引用的已确认版本、依赖、产物、退回和最终验收。GitHub 的合并结果作为证据关联，由产品验收人判定是否满足需求。 |
| 执行 | 执行器登记、能力与可用性、会话、执行尝试、工作区和结果。仅向有权限且支持所需能力的执行器分派。 |
| 人工决策 | 待答请求、可答人、类型、有效期、答复和投递状态。工作台按权限汇总不同 Agent 的请求。 |
| 审计 | 在调用方事务中追加业务事件，提供按需求、工单或尝试的时间线与脱敏导出。分析 Agent 使用只读视图，建议引用具体事件。 |

业务模块定义自己需要的最小接口。执行适配器提交执行事实，不能直接修改工单表；UI 和 GitHub 适配器也必须走相同应用入口。模块可以共享数据库和事务。跨模块的一个用例由应用服务协调，各模块仍负责自己的校验和状态。

## 两类外部接口

| 接口 | 最少要表达的行为 | 新接入时如何判断可用 |
| --- | --- | --- |
| Agent 适配器 | 启动一次尝试、上报事件和终态。结构化提问、原请求答复、取消、断线恢复分别声明能力。 | 用固定样例验证启动、结束、重复事件和异常退出。声明可交互的适配器还要验证两个会话同时提问、乱序答复和过期答复。 |
| 工具适配器 | 一个命名操作，声明输入与输出结构、所需权限及外部副作用。返回结果或可分类错误。 | 测试参数校验、拒绝授权、超时和脱敏。对有副作用的调用，只有具备幂等键或已核清前次结果时才能自动重试。 |

例如，Codex App Server 适配器把结构化请求映射为决策卡；只支持一次性命令的执行器只声明运行和结果能力。需要实时审批的工单在派单前检查此能力。接入 GitHub 查询 PR 可以单独实现只读工具；新增写操作时另行声明作用域和授权。新增适配器只增加实现、启动注册和契约用例。只有新增业务能力时才扩展公共接口。

对进程外消息和持久化事件，在边界校验结构并记录版本。优先新增可选字段。遇到未知审批类型或不兼容版本时将请求标为不支持，保留可诊断记录。添加破坏性变更时提供旧数据样例、兼容策略与回退说明。供应商凭据由各自的执行器管理；成员身份、执行器所有者、可用地区与操作权限共同限制路由。

### 本地 Codex 命令审批验证

首版选择本地 Codex App Server 承接运行中的人工审批。当前 TypeScript 验证适配器通过 `stdio` 启动子进程，每次尝试使用独立连接和调用方分配的工作区。适配器等 `turn/start` 回执确认轮次，再将匹配线程、轮次和工作区的普通命令审批交给调用方。每个审批使用独立的本地编号，按原连接和请求编号投递一次答复。调用方负责成员授权、工作区分配和审计持久化。 [Codex App Server 协议](https://learn.chatgpt.com/docs/app-server)

审批展示 App Server 对该请求提供的一次性选项。`accept` 是同意本次命令，`decline` 是拒绝当前命令，`cancel` 是取消本轮。工作台应把取消本轮作为明确的操作。旧响应省略选项时，适配器保留同意和拒绝两项。

连接中断时，待答审批失效，已投递且缺少回执的答复进入待核对。Codex 的 `serverRequest/resolved` 表示原请求已关闭。命令结果和整个轮次的结果分别以各自的执行事件为依据。

在仓库根目录运行 `npm run check`。两个模拟子进程使用相同的协议请求编号，分别收到倒序投递的拒绝和同意。测试覆盖重复答复、越界请求、消息乱序、断线和旧编号失效。

### 使用真实 App Server 复验审批

在仓库根目录使用 Node 22.17.1，并确保 `git` 和 `codex` 可执行。测试沿用本机 Codex 配置，为临时工作区单独设置模型端点和触发审批的命令规则。

```sh
SOULFLOW_TEST_NATIVE_CODEX=1 node --experimental-strip-types --test tests/codex-app-server.test.mts
```

在 Codex CLI 0.171.0-alpha.13 上，两个真实 App Server 进程在独立临时工作区收到回环服务生成的合成命令，均发出 `accept`、`cancel` 两项审批选项。测试先取消 B，再核对 A 仍在等待，最后取消 A。两次取消各自收到原生清理回执，轮次均变为 `interrupted`。第三次尝试主动关闭连接，待答审批失效，执行状态进入待核对。重复选择和跨会话选择均被拒绝。

原生同意后执行、真实模型调用、工作台成员权限和持久化审计仍待按下文验收。

## 从需求到验收的审计

需求和计划保留版本；工单记录来源版本；每次执行生成独立尝试 ID。决策、工具调用、产物、PR、评审和人工验收均关联对应工单或尝试。最小事件包括事件 ID、结构版本、操作者及身份类型、动作、对象及版本、关联 ID、结果、发生时间与服务端记录时间。大产物保存为受控引用，并记录版本或摘要。

一次业务状态变更与审计事件在同一个本地事务提交。外部调用无法加入该事务时，先持久化请求与待投递状态，再记录回执。回执不明时标记待核对，按操作 ID 查询或对账。将「用户已回答」「执行器已接收」「执行已继续」分别记录，各自需要对应证据。

决策绑定执行器身份、连接代次、会话、轮次和原始请求标识。答复时重新检查权限、请求有效性和待答状态，以原子条件更新接受一次答复。断线后先核对供应方状态；无法证明旧请求仍有效时停止投递。禁止把旧会话的许可复用给新尝试。

业务角色只能追加审计或追加更正记录。集中记录限于授权共享的事实与证据；凭据、环境变量值及未经筛选的终端输出不进入时间线或 GitHub。项目维护者需为导出、保留和备份设置访问范围。首次试点验证从备份恢复一张工单的完整历史。这里的设计能追踪业务操作，抵御数据库管理员篡改需要额外的独立存证。

### 本地审计与数据看板

工作台顶部的「数据看板」可查看过去 24 小时、7 天或 30 天的提交需求、决策答复、控件操作和视图切换。流程记录带流程 ID、尝试 ID、状态和适用的产物版本。Codex 运行记录解析 `thread/start` 返回的模型配置，在轮次启动成功后记录。审计保存已提交的需求与答复，过滤常见凭据及标记为敏感的问题。浏览器仅发送登记过的动作、视图和对象 ID；未提交的输入、坐标、外部网页和终端日志均不采集。

同一浏览器标签页和视图中，连续操作同一控件及对象的间隔满足 `SOULFLOW_AUDIT_REPEAT_CLICK_MS` 时算一次重复，默认 2,000 毫秒。切回前一视图的间隔满足 `SOULFLOW_AUDIT_QUICK_RETURN_MS` 时算一次快速返回，默认 30,000 毫秒。达到 `SOULFLOW_AUDIT_INSIGHT_MIN_COUNT` 时看板显示优化线索，默认为 3 次。三个变量均为正整数，窗口包含设定值。看板从 `GET /api/audit` 的 `thresholds` 读取口径。重启后用新阈值重新统计已有记录。

「最近记录」默认折叠，每类最多显示 60 条，展开后在区块内滚动。点击与视图切换的排行也在各自区块内滚动。业务记录来自服务端。浏览器操作用于分析界面使用情况。

本地 CLI 默认将演示与 Codex 的记录分别保存在 `.souflow/demo-audit.sqlite` 和 `.souflow/codex-audit.sqlite`。`SOULFLOW_AUDIT_DB` 可以指定其他路径。数据库只在本机使用，工作目录忽略 `.souflow/`。Codex 模式另在同一个数据库保存业务状态，详见[本机任务和决策恢复](#本机任务和决策恢复)。

### 在工作台认领 GitHub 工单

在本机用 `gh` 登录有权指派工单的账号，在 `.env` 中设置 `SOULFLOW_GITHUB_CLAIMS=1` 和与 `origin` 相符的 `SOULFLOW_PROJECT_GITHUB_REPO=owner/repository`，再运行 `npm run dev:codex`。个人模式默认使用当前 gh 账号。多人使用时，按[环境示例](../.env.example)配置独立的实施成员凭据，并用 `SOULFLOW_GITHUB_ACCOUNTS` 绑定各自的 GitHub 登录名。映射生效后，只有已绑定的实施成员可以领取。工作台按请求选取本机 gh 凭据，成员之间无需切换全局活动账号。

打开「GitHub 工单」，点击同步可查看待领取列表。点击领取后，souflow 选择最早创建且仍然开放、无人负责、本工作台未处理过的 Issue。连接层负责列举、指派和回读 GitHub，派发模块负责验权、记录认领和启动本机 Codex 核验。验收成员可以查看进度、展开清单、打开关联 PR。同步会从 GitHub 读取负责人，以及该仓库中使用关闭引用关联的 PR。

GitHub 允许同一张 Issue 有多位负责人。在同一持久化工作台内，先保存认领记录，再指派并回读唯一负责人，最后派发。成员同时领取时返回冲突，原成员用相同请求标识重试可以查看原结果。GitHub 网页或其他独立工作台也能改负责人，因此回读只能证明该时刻的归属。回执丢失、进程重启时遗留的认领和运行记录进入「待核对」，同步可查看远端现状。旧数据库首次启用此功能时使用新的检查点分区，关闭配置即可停止入口并保留记录。[GitHub 指派接口](https://docs.github.com/en/rest/issues/assignees#add-assignees-to-an-issue)

## 首次端到端验收

两张工单并行运行，各在独立工作区提出一个问题。操作者从同一页以相反顺序答复；核对请求只回到正确会话。再覆盖重复点击、无权答复和执行器断线。另一位成员仅凭获准查看的工单历史，应能解释计划来源、谁作了哪项决定、交付了什么、测试结果以及最终接受或退回的原因。模拟适配器和真实供应商分别记录验证结果。

### 对话首页与决策抽屉

在仓库根目录启动时，`npm run dev` 和 `npm run dev:codex` 会读取可选的 `.env`，终端中已有的环境变量优先。可以从 `.env.example` 复制模板。`SOULFLOW_DEMO_PORT` 控制端口，`SOULFLOW_DEMO_MAX_CONCURRENT` 和 `SOULFLOW_CODEX_MAX_CONCURRENT` 分别控制演示流程和 Codex 并发上限，默认分别为 24 和 4。

`SOULFLOW_PROMPT_MAX_LENGTH` 和 `SOULFLOW_ANSWER_MAX_LENGTH` 分别控制需求和自定义答复的长度，默认分别为 4,000 和 1,000，两者均可设为 1 到 16,000。页面从 `GET /api/decisions` 的 `inputLimits` 读取同一组上限。自由文本长度按浏览器输入框的 UTF-16 码元计数，一个表情可能占两个码元。预设选项按原问题中的标签验证。

souflow 通过 Codex App Server 运行规划，复用本机 Codex 登录。`SOULFLOW_CODEX_PLANNING_MODEL` 指定规划模型，`SOULFLOW_CODEX_EXECUTION_MODEL` 指定默认执行模型。变量留空时沿用本机 Codex 默认模型。指定模型后，适配器核对 App Server 回执的模型标识再启动轮次。

从已有项目续推时，可在 `npm run dev:codex` 的环境中设置 `SOULFLOW_PROJECT_PLAN`，例如 `docs/requirements-workflow.md`，并设置 `SOULFLOW_PROJECT_GITHUB_REPO` 为 `owner/repository`。后者需与本地 `origin` 对应，并使用已登录的 `gh` 只读查询最近八个 PR。每条需求固定一次本地 Git 提交，读取该提交内的计划和近期提交摘要；项目资料随规划发送给配置的模型，工作区未提交文件不在资料内。页面「本轮参考资料」标明所用提交、计划和 PR，以及未读到的来源。该轮后续拆单复用同一 Git 提交。

配置两个不同模型时，拆单为每张工单评估难度并说明理由，工单执行使用程序按难度选定的配置。常规工单使用执行模型，需要跨模块契约、权限、迁移或补查关键证据的工单使用规划模型。工作台在确认前展示选择理由，App Server 返回实际模型后留存记录。工单失败后的自动升级仍待接入。

如需 API key，凭据可填写在本机 `.env` 或通过启动进程的环境注入。Git 忽略实际的环境文件，仓库仅提交示例。使用 API key 时由 Codex 的认证或模型提供方配置读取相应变量。

在仓库根目录用 Node 22.17.1 运行 `npm run dev`，并打开 [souflow 首页](http://127.0.0.1:4173/)。左上角按钮展开最近对话侧栏，可创建和切换对话。「待决策」显示跨会话的待答数，点击可在当前页面打开右侧抽屉。

输入自然语言需求后，程序在后台依次推进调研、需求澄清、技术选型、开发文档和拆单。对话显示原始需求和当前状态。已生成的产物在当前对话的「查看项目文档」中按文档浏览，供项目审阅与后续拆单使用。

1. 输入一条需求。调研样例完成后，打开「待决策」，选择这条需求并答复首版范围。
2. 提交后，该事项从待答列表移除，抽屉保持打开以便继续处理。原需求继续推进，返回对话后可在「查看项目文档」浏览 PRD、开发计划和工单草稿。
3. 抽屉列表可以独立滚动，切换待答事项时保留草稿。模拟断线可使待答请求失效，后续状态可在数据看板的流程记录核对。

运行 `npm run dev:codex` 可使用本机已配置的 Codex CLI。如果演示占用 4173，可用 `SOULFLOW_DEMO_PORT=4174 npm run dev:codex`。每个阶段运行独立的只读规划轮次，程序将已生成的产物传给下一阶段，收到符合本阶段结构的成功产物后才推进。`item/tool/requestUserInput` 映射为抽屉中的待决策事项，通过原连接回复。秘密输入和命令授权由适配器拒绝。规划会话禁用继承的 MCP 服务、插件、应用和钩子。 [Codex App Server 协议](https://learn.chatgpt.com/docs/app-server)

本地服务只监听回环地址。已完成的开发计划可准备本地工单。两位成员可使用下文的本机模式。真实模式的「原提问已关闭」来自 `serverRequest/resolved`，产物必须来自完成后的有效输出。当前支持 souflow 发起的本机 Codex 会话。

### 本机任务和决策恢复

使用 `npm run dev:codex` 启动。原目录、`SOULFLOW_AUDIT_DB` 和登录模式相同时，重新启动会恢复需求对话、已完成的规划阶段及版本、工单批次和验收历史。SQLite 同一事务写入业务状态和相应审计事件。成员登录仍读取环境配置，数据库保留角色和操作记录。可在同一登录模式下轮换密钥。一个数据库同一时刻由一个工作台持有，切换工作区或登录模式请另选数据库路径。

- **规划中断。** 在最近对话打开原需求。实施成员点「继续未完成的规划」时，已完成的阶段沿用原产物，未完成阶段从已保存的资料和版本开启新 Codex 轮次。「中断的决策记录」保留失效问题和回执待核对的答复状态。若新轮次仍需要决策，成员须答复新卡。旧卡的服务端答复地址返回 409。
- **等待前置补丁验收。** 重启后，待决策抽屉里的补丁卡仍引用同一批次、工单及 SHA-256。验收成员可以审批；实施成员点「继续派发剩余工单」后，已获批准的原版补丁可供剩余工单使用。读取和应用时均验证补丁版本。
- **工单执行中断。** 不能确认结果的活动工单标记为失败待核对，原批次及已保存产物留在历史。核对后可准备新批次。已提交的最终验收仍由验收成员按原计划版本处理。

本机产物放在数据库旁的 `<数据库路径>.artifacts/` 中。备份前先停止工作台，并成对备份数据库及产物目录。恢复时沿用原有路径。首次升级会在已有 SQLite 内添加业务状态表并继续读取历史审计；此前仅保留审计的版本无法从日志重建业务状态。内存演示在重启后重新开始。回滚前保留这两份数据，旧版可读取审计。

[查看本机重启、断线和恢复实测](acceptance/b4-recovery.md)。

### 本机核验工单实验

用 `npm run dev:codex` 和现有 Codex 登录，在对话完成后进入「本地执行工单」。准备工单会调用规划模型拆分，由程序校验验收覆盖、引用、依赖环和资料路径。界面展示待确认工单、开发计划版本及固定的 Git 提交。确认后，执行模型通过独立 App Server 会话生成核验报告。可并行的工单按 `SOULFLOW_DISPATCH_MAX_CONCURRENT` 启动，默认 2；依赖单等所需报告齐备后启动，失败会阻塞后续依赖。

此模式的交付物是核验报告。执行会话的环境工具已关闭，由程序从该提交的普通 Git 文件对象提供经核对的资料与前置报告。程序把报告及 `run.json` 写入本机产物目录下的独立批次目录，并将确认和执行结果写入审计。各报告仍需人工验收。

### 调度面板

在 `npm run dev:codex` 的工作台顶部打开「调度面板」，可查看调度器、执行设备和活动 Codex Agent 的连接。每条支路显示该 Agent 正在处理的需求步骤或工单。工单进展根据实际派发、等待前置或验收、执行结果和产物状态更新。点击任一节点或工单，右侧打开详情，按节点范围展示会话和时间线。App Server 回执到达后显示实际模型和会话 ID，调度器详情可浏览最近结束的 24 条会话。执行中的路径有流动动效，系统启用减少动态效果、页面在后台或服务连接中断时暂停。

面板从本地调度和 App Server 的状态取数。前置依赖未满足的排队工单在真正启动后才获得会话 ID，Codex 会话结束后可到工单核对产物是否生成和验收。可用 `SOULFLOW_HOST_NAME` 指定显示名，默认使用操作系统主机名。当前显示此服务启动的本机 Codex 会话，跨机器登记、心跳和 Codex Desktop 已有对话需另接。参考机器在线状态和任务时间线的成熟设计。 [GitHub Actions Runner](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/monitor-and-troubleshoot) · [Temporal Web UI](https://docs.temporal.io/web-ui) · [Dagster 运行时间线](https://dagster.io/docs/guides/operate/webserver)

### 调度本地代码工单

规划就绪后，在「本地执行工单」选择「编写代码」。负责人确认开发计划版本、仓库提交和每单可编辑文件后，服务在独立的快照目录为每单启动本机 Codex 会话。工单可修改已纳入 Git 的普通源文件、测试和文档。没有先后关系的工单可以并行，编辑范围须互斥。需要改同一文件的工单必须按依赖串行。

执行模型根据提供的文件内容返回文本替换和交付说明。服务核对路径、原文和范围，再将改动写入该工单的工作目录并保存 `changes.patch`。涉及已脱敏的凭据片段时，改用未脱敏的原文锚点或缩小工单范围。

有后续工单的补丁生成后，打开「待决策」，根据卡片中的本地补丁路径和 SHA-256 复核这份产物。逐张通过所需前置补丁后，下游才开始。拒绝、前置失败或补丁内容变更会阻止相关下游派发。派发时服务从固定 Git 提交重建独立工作区，按依赖顺序应用已验收的祖先补丁，共享祖先只应用一次。下游的参考资料和可编辑文件均反映已应用的改动。工单和审计记录保存验收结果、补丁摘要及上游产物引用。

交付人可在基线一致的独立工作区运行 `git apply --check -p2 <补丁文件>` 核对补丁。有依赖的补丁需在按顺序应用对应前置补丁后再核对。测试、提交、推送和 PR 由交付人复核后执行。前置验收按批次、计划版本和补丁摘要绑定。运行或等待前置验收的批次占用本地工作台的派发名额。重启后，符合[恢复条件](#本机任务和决策恢复)的批次由实施成员确认续派。

工作台接口为原始请求和每份规划产物返回独立 ID、整数版本和上游 `{ id, version }` 引用。引用在启动阶段前由程序根据实际输入记录，并随阶段交给 Codex。PRD 和开发计划各自编号，两份文档在同一个阶段校验通过后一起记录。工单草稿集引用开发计划的具体版本，开发计划可再追到 PRD 和技术选型。

对话就绪后，在「项目文档 → 开发计划」保存修改会生成同一计划的新版本，并记录被替换的版本。旧计划、旧工单草稿与旧派发批次可查。新批次重新拆单并接受确认；用旧批次编号调用执行会收到冲突响应。同一对话的批次在执行或等待前置验收时，计划修改须等该批次结束。并发保存以请求中的原版本核对，只接受一份改版。发生冲突时，浏览器保留未保存的草稿，由操作者核对当前版本后选择是否带入。

计划编辑沿用已经生成的需求验收条件。需求范围变化仍需要重新澄清。Codex 模式将计划、版本历史及工单确认保存在本机 SQLite，审计保留版本变更事件。

### B3 两位成员交付与验收

在本机 `.env` 设置 `SOULFLOW_MEMBER_IMPLEMENTER_KEY` 和 `SOULFLOW_MEMBER_REVIEWER_KEY`，分别生成不同的随机值。可用 `openssl rand -hex 32` 生成。启动 `npm run dev:codex` 后，在两个独立的浏览器配置文件里访问同一回环地址。浏览器登录用户名为 `implementer` 和 `reviewer`，顶部显示当前身份。两项均不配置时沿用个人模式。

| 身份 | 能做什么 |
| --- | --- |
| 实施成员 | 发起需求并答复澄清、修订计划、准备和启动本机工单、提交已完成批次。 |
| 验收成员 | 在待决策中通过或拒绝前置补丁。在本地执行工单中查看交付说明和产物，退回修订或通过最终验收。 |

两位成员都能查阅共享项目的对话、工单和审计。直接调用接口同样校验身份和操作权限。提交后冻结当前计划。退回须填写原因，实施成员在项目文档保存新计划版本，再重新拆单、执行和提交。若该版本已被退回，换一种工单类型也须先修订计划。旧批次的历史回执保留，旧批次无法重新提交或通过。通过最终验收会核对报告和补丁，冻结该版并记录成员、计划版本、仓库提交、产物和备注；同一状态的重复操作只记录一次。

两位成员模式只在同一主机的回环地址上使用。此处验证两个独立应用身份，远程成员登录及双机接入在后续验证。验收操作在当前进程内生效，SQLite 负责保留审计证据。软件内的「最终验收已通过」对应这一个本地批次，项目发布状态在相应发布工作流中登记。

```sh
SOULFLOW_TEST_NATIVE_CODEX=1 node --experimental-strip-types --test tests/codex-decision-inbox.test.mts
```

原生用例使用 Codex CLI 0.171.0-alpha.13 与本地回环模型夹具。两个真实 App Server 分别派发相同问题 ID，测试通过工作台接口按 B、A 顺序答复，并在各自模型请求中核对返还的答案。随后测试从对话入口推进五个阶段，核对澄清前只启动前两阶段，回答后得到 PRD 和工单草稿。
