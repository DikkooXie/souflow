# 从自然语言需求到开发文档与工单

这是 souflow 工作台面向项目成员提供的核心功能。成员用自然语言描述要解决的问题，系统提取意图、按需澄清，形成可编辑的结构化需求；随后生成 PRD 和开发计划，最后依据确认的文档拆出 Agent 可以领取和验收的工单。输入已经清楚时，直接展示结构化草稿供确认。

产品流程设计，供两位开发者和执行 Agent 共用。借鉴 Matt Pocock 的 [grilling](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/productivity/grilling/SKILL.md)、[to-spec](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/engineering/to-spec/SKILL.md) 和 [to-tickets](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/engineering/to-tickets/SKILL.md)。个人技能可以发起访谈；服务端以自己的状态和证据决定是否进入下一步。

| 阶段 | Agent 起草什么 | 系统检查什么 | 谁决定通过 |
| --- | --- | --- | --- |
| 记录意图 | 复述用户、目标、范围，列出可能解释 | 保存原文、提交者与修订号。每条事实引用可访问证据，无法查证的标为假设 | 提出人可以纠正意图 |
| 澄清 | 先查代码和知识页。只问会改变范围、授权或验收的问题；一轮可合并互不依赖的问题 | 问题有 ID、前置依赖和阻塞标志；答案绑定具体问题及修订。未答、被撤回、来源冲突均有明确状态 | 有权成员答复，或明确将事项排除出本版范围。模型推荐和超时均不算同意 |
| 形成结构化需求 | 提取需求 ID、使用者、场景、目标、范围内外、约束、带 ID 的验收条件和待决项；保留原文及问答引用 | 校验必填项、引用和修订号。未决假设保持可见，存在阻塞项时返回澄清 | 提出人可直接修改字段并确认需求版本 |
| 生成开发文档 | PRD 写明要解决的问题、用户行为、范围和验收条件；开发计划引用该 PRD，写明可交付步骤、依赖和验证办法。接口或数据结构有变化时补相应设计说明 | 两份文档均引用输入版本；计划步骤可追溯到需求与验收项。新增业务假设返回需求层核实 | 负责人可一并审阅两份文档，确认具体版本组合后进入拆单 |
| 生成工单 | 每单描述可独立验证的行为、所需能力、依赖、关联验收条件及验证办法 | 检查工单 ID 唯一、依赖存在且无环、验收引用有效、每项必需条件都有承接工单 | 成员确认拆分与依赖，批准的工单绑定计划版本和拆单版本 |
| 派发与验收 | 执行器返回产物、测试结果和局限 | 服务端读取自己的批准记录、最新版本、权限、能力、前置单验收与领取状态。原子领取并记录审计；重复领取返回原结果 | 另一位获授权成员按工单验收，接受或写明退回理由 |

**职责边界。** 模型输出只进入候选数据。服务端校验结构、状态、引用和版本。评审会话核对内容并报告缺口，成员决定产品取舍和执行授权。模型输出中的“已批准”、自报身份或“测试通过”都不能生成审批记录。每次转换记录输入版本、操作者、结果、拒绝原因和依据。计划改版保留历史，对受影响的未开始工单暂停派发；已运行的尝试提示负责人处置。访谈与生成文档本身不触发外部发布或编码。

## 从已有项目接着做

souflow 首版要让负责人输入「继续推进 souflow 开发」，在一个对话里核对目标和范围，随后能看到按依赖派出的独立工单、GitHub 交付和待验收结果。首版顺序以可验证的工作为单位：

1. **派发前质量校验。** 检查结构化需求、PRD、开发计划和候选工单是否追溯到同一轮意图和验收条件。本地和 GitHub 代码工单通过结构检查和独立内容复核后进入执行授权。
2. **首版试用 · 双机单账号代码协作。** 使用两台实体电脑，各自在本地用同一个 Codex 账号执行一张不同的真实工单。通过共同的 GitHub 仓库交接、测试和提交关联 PR。按下文验收。
3. **服务器版 · 网页设备配对与远程代码执行。** souflow 部署在服务器，由设备主动连接。用户登录网页后绑定设备、选择执行目标并跟进代码、测试和 PR 进度。具备多个独立 Codex 登录后，在不同设备上验证多账号派发、归属和接力。

范围清楚、改动局部且验收直接的工单按常规难度处理。涉及跨模块契约、权限、迁移或缺少关键证据的工单使用高难度模型。按实际工单内容选档，并在工单上留理由供审阅。

计划描述预期行为。当前完成度结合仓库、PR 和已确认的验收记录判定。

首版验收包括从真实 GitHub 仓库主动认领无人负责的 Issue、重复事件只派发一次、单机同账号多会话，以及双机同账号开发。工单开 PR 后等待评审，上游合并后自动唤醒依赖工单。完整条件与本机实测进度见[项目首页](../README.md#首版怎样才算达标)。

### 派发前质量校验

本地和 GitHub 的候选工单复用[结构校验](../src/planning/validate-ticket-plan.mts)。服务端核对上游版本、验收覆盖和依赖，每项工单验收都要列出可执行步骤与预期结果。独立的只读 Codex 会话使用本轮产物和固定 Git 提交核对范围、依据和验证。范围明确的小工单集中看验收，新模块与权限、持久化和跨模块接口优先核对易返工的假设及失败路径。服务端核对复核引用确实出现在本轮材料。

采用 Spec Kit 的只读跨文档核对方式，借鉴 OpenSpec 将结构错误作为阻塞条件。用可重复的规则评估版本和结构，用内容复核判断语义，用人来作实质产品决定。在现有规划和审计中接入这些检查，避免引入第二套文档目录或执行流程。[Spec Kit](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md) · [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md#validation-commands) · [Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) · [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

| 检查对象 | 派发前应能回答 | 需要拦截的示例 |
| --- | --- | --- |
| PRD | 哪个用户在什么场景完成什么？首版范围及失败场景怎样验收？ | 用户只确认了录音生成纪要，PRD 把实时会议当作已批准范围。 |
| 开发计划 | 复用当前仓库的什么能力？方案为何适合本次约束？哪个关键假设要先实测？ | 计划声称已有转写服务，但引用的仓库版本或资料无法支持这一主张，并且后续开发依赖它。 |
| 工单 | 每项验收由谁完成、产出什么、如何独立验证？后续工单等哪个结果？ | 工单挂了「重复确认只发送一次」的验收编号，但所有验证只覆盖首次发送。 |

先从一条「上传录音生成纪要，人工确认后发送待办」的完整样例以及上表反例做回归。通过条件如下。

- 合格样例进入执行授权。漏项、越出已确认范围、关键依据缺失或必需依赖有误时，阻止派发，并定位到具体版本、验收项或工单。普通修订退回草稿处理；确实影响产品范围、权限或验收的取舍才进入「待决策」。
- 审计关联需求、PRD、计划和工单版本，以及复核结论、来源和阻塞原因。改版后重新核对受影响的产物；旧复核结论和旧授权无法启动新版工单。
- 本地准备批次和 GitHub 选单都使用同一套规划版本规则。在确认执行或授权认领时再次核对产物和工单摘要。复核超时、引用无法核对或缺少可靠依据时，可以重新准备。旧批次没有校验凭据时须重新准备，已交付的记录继续用于审计。

### 首版双机单账号试用

使用两台实体电脑和同一个已登录的 Codex 账号。选择同一个真实仓库里的两张不同工单，分别在各自机器的本地会话与独立 Git 工作区完成开发和测试，提交可追溯到对应 Issue 的 PR。至少验证一次通过 GitHub 的跨机交接：上游 PR 合并后，下游电脑从合并后的提交开始或继续其工单。保存两台电脑各自的执行或测试截图，以及关联 Issue、PR、提交和 CI，核对负责人和工单没有串单。此试用以各自机器本地启动执行，GitHub 承载协作和交接。

[B6 局域网双机实测与截图（PR #42）](https://github.com/DikkooXie/souflow/pull/42)记录 Mac 接入包、两台实体 Mac 在线、只读核验在断线后从 `1/3` 恢复到 `3/3`，以及单次领取。它提供设备接入和恢复的证据，双机代码协作仍待实测。单机同账号多会话已有[实测证据](acceptance/session-account.md)。单机跨账号的[接入和测试记录](acceptance/codex-account-dispatch.md)作为以后多机多账号试验的参考。

## 编排长期开发计划

每个阶段都应交付一个当期能用的结果。决定先做哪项时，比较用户价值、依赖和实现成本。在其他条件相近时，优先做能替下一阶段省去实际工作的那一项。比如先让开发调度器接手 souflow 自身的开发工单，后续模块便可以直接沿用已验收的派发和交付流程。

| 规划时回答的问题 | 在计划中留下什么 |
| --- | --- |
| 这一阶段交付后，谁能用它完成什么？ | 一个具体场景、可观察的验收条件，以及要复用的已有能力和版本。 |
| 哪项后续工作会因此变容易？ | 指出下一张候选工单、它会调用的能力，以及可省去的手工步骤。把潜在复用收益标为预期，等到具体场景出现再提取共用接口。 |
| 怎样判断这次排序值得？ | 在下一阶段选一张真实工单使用上阶段的交付，关联工单、PR 和审计记录。与范围相近、验收标准相同的历史工单对照，并计入接入和维护成本。 |

复盘时先核对质量和预算，再看人工介入、返工、交付耗时和模型用量。把实际省下的步骤、增加的工作和适用条件写回项目知识库。缺少可比样本时保留观察，继续收集证据。下一轮规划用这些结果决定继续复用、调整接口，还是把精力转向更迫切的需求。

## 同一条需求经过各阶段的样子

| 产物 | 示例内容 |
| --- | --- |
| 成员原话 | “我想把筛过的工单导出给同事看。” 经追问，成员选 CSV，并确认导出顺序与页面一致。 |
| 结构化需求 REQ-1 v1 | 角色为项目成员，场景为在工单列表筛选后分享结果。AC-1 要求 CSV 只含命中且当前成员可见的工单；AC-2 要求行序与列表一致。示例中两项均由成员确认。 |
| PRD v1 | 引用 REQ-1 v1。用户在筛选结果页点击导出即可取得 CSV。列出 AC-1、AC-2，以及供审阅者对照的样例输入和期望输出。 |
| 开发计划 v1 | 引用 PRD v1。步骤 S1 打通筛选结果到 CSV 的导出并验证可见范围；S2 在 S1 基础上支持保留当前排序，以降序列表验收。 |
| 工单 | T1 对应 S1、AC-1：交付可演示的筛选导出，验证无权查看的行未被导出。T2 对应 S2、AC-2，依赖 T1：交付排序一致的导出，以样例逐行对照。两单均绑定计划 v1。 |

原型演示时，成员应能从 T2 点回 S2、PRD v1、REQ-1 v1 和“保留排序”的原始答复。若改为按创建时间导出，系统应能指出 AC-2、S2 和 T2 需要重新审阅，并保留旧版引用。

**最小验收场景。** 用“导出工单”发起访谈，先确认导出的范围，再生成带验收 ID 的方案与工单。以下反例应分别给出可定位的失败原因：

- 模型推荐“导出整个项目”，用户尚未回复；系统保留为待答。
- 两张工单互相依赖，或新拆分漏掉关键验收条件；拆分无法提交确认。
- 用户确认 v1 后修改为 v2；旧批准无法触发新版派单。
- 两个执行器同时领取同一张单；只产生一次有效尝试。
- 执行器报告完成但缺少验收证据；工单进入待补证或待审，人工可退回。

拆单中的纯结构规则可在仓库根目录用 Node 22.17+ 运行 `node --experimental-strip-types --test tests/ticket-plan.test.mts`。产品状态持久化、权限校验和外部派单由后续实现分别验收。
