# 从自然语言需求到开发文档与工单

这是 souflow 工作台面向项目成员提供的核心功能。成员用自然语言描述要解决的问题，系统提取意图、按需澄清，形成可编辑的结构化需求；随后生成 PRD 和开发计划，最后依据确认的文档拆出 Agent 可以领取和验收的工单。输入已经清楚时，直接展示结构化草稿供确认。

产品流程设计，供两位开发者和执行 Agent 共用。借鉴 Matt Pocock 的 [grilling](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/productivity/grilling/SKILL.md)、[to-spec](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/engineering/to-spec/SKILL.md) 和 [to-tickets](https://github.com/mattpocock/skills/blob/abeeaf95660ba9e8b7c753eb38f441ca707a8823/skills/engineering/to-tickets/SKILL.md)。个人技能可以发起访谈；服务端以自己的状态和证据决定是否进入下一步。

| 阶段 | Agent 起草什么 | 系统检查什么 | 谁决定通过 |
| --- | --- | --- | --- |
| 记录意图 | 复述用户、目标、范围，列出可能解释 | 保存原文、提交者与修订号。每条事实引用可访问证据，无法查证的标为假设 | 提出人可以纠正意图 |
| 澄清 | 先查代码和知识页。只问会改变范围、授权或验收的问题；一轮可合并互不依赖的问题 | 问题有 ID、前置依赖和阻塞标志；答案绑定具体问题及修订。未答、被撤回、来源冲突均有明确状态 | 有权成员答复，或明确将事项排除出本版范围。模型推荐和超时均不算同意 |
| 形成结构化需求 | 提取需求 ID、使用者、场景、目标、范围内外、约束、带 ID 的验收条件和待决项；保留原文及问答引用 | 校验必填项、引用和修订号。未决假设保持可见，存在阻塞项时返回澄清 | 提出人可直接修改字段并确认需求版本 |
| 生成开发文档 | PRD 写明要解决的问题、用户行为、范围和验收条件；开发计划引用该 PRD，写明可交付步骤、依赖和验证办法。接口或数据结构有变化时补相应设计说明 | 两份文档均引用输入版本；计划步骤可追溯到需求与验收项。新增业务假设返回需求层核实 | 负责人可一并审阅两份文档，确认具体版本组合后进入拆单 |
| 生成工单 | 每单描述可独立验证的行为、所需能力、依赖、关联验收条件及验证办法 | 检查工单 ID 唯一、依赖存在且无环。所有验收项须有归属，可分给新工单、关联 Issue 或整批验收 | 成员确认拆分与依赖，批准的工单绑定计划版本和拆单版本 |
| 派发与验收 | 执行器返回产物、测试结果和局限 | 服务端读取自己的批准记录、最新版本、权限、能力、前置单验收与领取状态。原子领取并记录审计；重复领取返回原结果 | 另一位获授权成员按工单验收，接受或写明退回理由 |

**职责边界。** 模型输出只进入候选数据。服务端校验结构、状态、引用和版本。评审会话核对内容并报告缺口，成员决定产品取舍和执行授权。模型输出中的“已批准”、自报身份或“测试通过”都不能生成审批记录。每次转换记录输入版本、操作者、结果、拒绝原因和依据。计划改版保留历史，对受影响的未开始工单暂停派发；已运行的尝试提示负责人处置。访谈与生成文档本身不触发外部发布或编码。

## 从已有项目接着做

souflow 首版要让负责人输入「继续推进 souflow 开发」，在一个对话里核对目标和范围，随后能看到按依赖派出的独立工单、GitHub 交付和待验收结果。首版顺序以可验证的工作为单位：

1. **派发前质量校验。** 检查结构化需求、PRD、开发计划和候选工单是否追溯到同一轮意图和验收条件。本地和 GitHub 代码工单通过结构检查和独立内容复核后进入执行授权。
2. **首版试用 · 双机单账号代码协作。** 使用两台实体电脑，各自在本地用同一个 Codex 账号执行一张不同的真实工单。通过共同的 GitHub 仓库交接、测试和提交关联 PR。按下文验收。
3. **服务器版 · 网页设备配对与远程代码执行。** souflow 部署在服务器，由设备主动连接。用户登录网页后绑定设备、选择执行目标并跟进代码、测试和 PR 进度。具备多个独立 Codex 登录后，在不同设备上验证多账号派发、归属和接力。

范围清楚、改动局部且验收直接的工单按常规难度处理。涉及跨模块契约、权限、迁移或缺少关键证据的工单使用高难度模型。按实际工单内容选档，并在工单上留理由供审阅。

计划描述预期行为。当前完成度结合仓库、PR 和已确认的验收记录判定。

首版验收包括从新需求自动拆单、复核与授权、在真实仓库自动创建 Issue，再把本批 Issue 派给 Codex。用一条尚无对应 Issue 的实际需求走完整流程，并追溯计划版本、建单回执、执行会话、测试和关联 PR。主动认领已有无人负责 Issue、避免重复派发、单机同账号多会话与双机同账号开发均应保留独立证据。工单开 PR 后等待评审，上游合并后自动唤醒依赖工单。完整条件与本机实测进度见[项目首页](../README.md#首版怎样才算达标)。

### 派发前质量校验

本地和 GitHub 的候选工单复用[结构校验](../src/planning/validate-ticket-plan.mts)。服务端核对上游版本、验收覆盖和依赖，每项工单验收都要列出可执行步骤与预期结果。独立的只读 Codex 会话使用本轮产物和固定 Git 提交核对范围、依据和验证。范围明确的小工单集中看验收，新模块与权限、持久化和跨模块接口优先核对易返工的假设及失败路径。服务端核对复核引用确实出现在本轮材料。

GitHub 选单可引用同一提交中直接相关的只读源码，例如承接调用的服务端路由。校验和执行使用该版本的材料，编辑权限仍由授权卡列出的文件决定。上游合并改变引用的源码时，派发暂停并重新核对。

主机和代码设备通过 `.env` 的 `SOULFLOW_CODE_EDIT_FILE_MAX_BYTES` 配置单文件编辑上限。设备上线时上报实际能力，只领取本机能够读取和核对的快照。旧设备按原先的单文件上限处理。主机和设备都检查固定提交、文件摘要与字节数，再接受补丁。

补丁接收使用独立的容量上限，先核对 JSON、编辑数、原文锚点和文件范围，再安装依赖。格式或锚点等可修正问题交给同一 Codex 账号纠正一次。工作台审计保存固定错误码、编辑序号和必要的数量，原始回复不入库。隔离检查失败可沿同一授权另重试一次。重试使用新工作区并复核原负责账号、Issue 内容和批准的源码。越权、脱敏字段以及发布回执待核对时暂停。维护者可用 `SOULFLOW_GITHUB_RECOVER_FAILED_ISSUE` 显式恢复一张未进入发布、仅有旧版失败诊断的工单。恢复次数写入原记录，重启不会再次触发。

维护者可用 `SOULFLOW_GITHUB_REVIEW_FIX` 续修一张已经提交的原工单。参数绑定 Issue、PR、当前提交、原目标分支和原批准文件的子集，并给出本次评审要求。souflow 从该提交创建独立工作区，用原授权开发和隔离检查，通过后只用原 GitHub 账号快进原 PR 的分支。相同提交只启动一次，发布结果不确定时只回读已有 PR。

交付的两类复核都已出具结论且当前提交被拦截时，原发起者可在「待决策」确认关联修复。卡片显示将发布的 Issue 正文，包含原 Issue、PR、当前提交、复核回执和原授权文件。授权后系统创建或回读该修复 Issue，并按原文件范围在同一 PR 续修。GitHub 写入结果不确定时可刷新工单列表回读同一次请求。完成后保留修复 Issue 和旧复核，重新核对新提交的两类证据。

采用 Spec Kit 的只读跨文档核对方式，借鉴 OpenSpec 将结构错误作为阻塞条件。用可重复的规则评估版本和结构，用内容复核判断语义，用人来作实质产品决定。在现有规划和审计中接入这些检查，避免引入第二套文档目录或执行流程。[Spec Kit](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md) · [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md#validation-commands) · [Anthropic](https://www.anthropic.com/research/demystifying-evals-for-ai-agents) · [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

| 检查对象 | 派发前应能回答 | 需要拦截的示例 |
| --- | --- | --- |
| PRD | 哪个用户在什么场景完成什么？首版范围及失败场景怎样验收？ | 用户只确认了录音生成纪要，PRD 把实时会议当作已批准范围。 |
| 开发计划 | 复用当前仓库的什么能力？方案为何适合本次约束？哪个关键假设要先实测？ | 计划声称已有转写服务，但引用的仓库版本或资料无法支持这一主张，并且后续开发依赖它。 |
| 工单 | 每项验收由谁完成、产出什么、如何独立验证？后续工单等哪个结果？ | 工单挂了「重复确认只发送一次」的验收编号，但所有验证只覆盖首次发送。 |

先从一条「上传录音生成纪要，人工确认后发送待办」的完整样例以及上表反例做回归。通过条件如下。

- 合格样例进入执行授权。漏项、越出已确认范围、关键依据缺失或必需依赖有误时，阻止派发，并定位到具体版本、验收项或工单。普通修订退回草稿处理；确实影响产品范围、权限或验收的取舍才进入「待决策」。
- 审计关联需求、PRD、计划和工单版本，以及复核结论、来源和阻塞原因。改版后重新核对受影响的产物；旧复核结论和旧授权无法启动新版工单。
- 本地准备批次和 GitHub 选单都使用同一套规划版本规则。在确认执行或授权认领时再次核对产物和工单摘要。复核超时、引用无法核对或缺少可靠依据时，可以重新准备。旧批次没有校验凭据时须重新准备，已交付的记录继续用于审计。

有内容复核结论的批次被拦截后，原发起者可在对话中选择「按当前版本重新规划」。工作台重新读取当前仓库提交和项目计划，带上已答澄清、上一版验收条件和拦截意见。原需求编号保持一致，各阶段生成新版本并引用新版上游。旧文档继续在归档页可读，旧批次和授权记录仍可追溯。新批次重新经过质量复核和执行授权。已授权的 GitHub 批次、正在派发或待验收的本地批次需要先按各自流程处理。

逐单复核中断时，如果同一计划和提交已保存可核对的源码拦截意见，原发起者也可沿用意见重新规划。旧批次不会获得授权。仅有超时或引用错误、没有实质拦截意见时，仍可重新复核原批次。

选中的现有 Issue 缺少本轮验收覆盖时也进入原对话的重新规划入口。工作台给出缺失编号。复规划核对已实现能力、已有工单范围和新增缺口，保留原验收，并按新版重新复核与授权。此前同类的未授权失败记录在重启时恢复为可重新规划状态。

候选范围只覆盖部分验收时，选单在固定资料内重新判断一次。真实新结果可以转入新建 Issue 的拆分，已有候选作为避免重复与核对前置的依据。需先通过完整的结构校验与独立内容复核，再由成员授权创建。仍有覆盖缺口时保留可追溯的拦截理由。

项目计划或候选正文引用同仓库编号时，通过 GitHub 确认条目类型，保留 Issue 或 PR 的正文和状态。PR 还记录头提交与合并提交，仅作为已有交付依据。已关闭、已分配和读不到正文的引用分别标明。明确前置优先装载，默认使用 `SOULFLOW_PROJECT_GITHUB_REFERENCE_LIMIT` 读取最多 24 条引用，超出时在「本轮参考资料」提示。关联资料版本随项目提交冻结，认领候选仍由仓库当前状态和授权决定。

新建工单先按工单核对固定提交上的编辑文件和只读参考，再用逐单证据复核整个批次的验收映射、依赖和排序。下游复核使用同一版开发计划和直接前置约定，核对上游合并后会提供的接口。保存每张工单的提交、路径、内容摘要和可核对的源码引用。任一工单少读、复核拦截或证据不全时，批次不能授权。批次复核未完成时保留已取得的逐单结果。技术依据或验证缺项可以在原计划内自动修订一次，修订后完整重审。范围冲突回到原对话处理。旧版尚未授权且须补齐源码复核的草稿可以沿用原计划和同一批次重新校验。

逐单源码复核的回执若无法解析、超出结论或引用限制，或引用与原文不符，系统用同一份固定资料、带校验原因重查一次。有效的拦截结论直接保留。两次回执都无效时仍停止授权，保留其他工单已核对的结论。

新建工单的授权卡会列出由直接上游交接的只读路径。上游合入默认分支后，工作台回读原 Issue 与确切 PR，检查从原基线到执行提交的 Git 第一父历史。只有对应的获批上游合并提交可以改变该路径。下游编辑范围、项目计划或其他只读资料有变化时停止派发。按实际合并提交重新独立复核源码，保存两个版本、合并凭据及复核回执，通过后才交给执行器。旧授权没有交接约定时沿用原来的固定源码校验。

开发计划须说明哪些条件缺失会阻止安全开工，以及哪些证据要到交付时取得。例如，外发数据边界和确实必需的上游接口在开工前确定，工单实现后产生的请求回执和真实交付结果在执行验收时取得。真实联调尚缺资源时记录准备人和需要的阶段。派发前复核仍核对权限、固定范围、依赖及验证设计，执行和验收回执按实际结果记录。

新建 GitHub 工单时，项目文档和符合复核大小限制的源码可以作为只读资料。拆单时按冻结文件大小检查每张工单的资料总量。授权卡仍逐单列出可编辑的源码和测试文件。资料引用不在冻结清单、重复或超限时，系统用同一份计划和文件清单修正一次，再重跑校验。

复核资料默认每次最多 256 KiB。用 `.env` 的 `SOULFLOW_QUALITY_SOURCE_INPUT_MAX_BYTES` 调整，单位为字节，最高 512 KiB。拆单和读取采用同一个配置。文件内容来自固定提交，读取后的脱敏资料按实际字节再次计入预算。

项目规划也从固定提交准备只读源码。优先核对原请求、上一轮复核、项目计划和候选工单指向的文件。只在文件名唯一时补全简写。数量通过 `SOULFLOW_PLANNING_SOURCE_MAX_FILES` 配置，默认 8 个，沿用复核资料字节预算。「本轮参考资料」显示路径、读取状态和内容摘要。模型收到的是脱敏正文，数据库只持久化可追溯的摘要。中断后按同一提交和摘要恢复，资料无法回读时停止本轮。

拆分新工单时把可独立验证的行为分给工单。涉及多张工单、设备分配或合并后唤醒的验证列为整批验收。已有交付的回归可引用本轮冻结的已有 Issue 正文。两类另行验收都需明确步骤和预期，随批次复核并展示在授权卡与原对话，实际测试前保持待验收。仅新工单创建 Issue 和派发；真正阻塞本单的前置依赖继续在依赖链核对。

每张新工单至少关联一项自己能够验证的验收。同一个编号可由多张工单分别验证不同部分。草稿漏填归属，或把同一可编辑文件分给不同 GitHub 工单时，系统可在原计划范围内修正一次，随后重新核对全部条件。文件冲突会指出路径和涉及的工单。即使是串行工单，每个可编辑文件也只归属一张工单。

新建 GitHub Issue 的工单逐张交付一个可独立演示的用户结果，并列出验收操作和预期、允许修改的文件、优先理由及真实阻塞前置。工单按批准计划的优先顺序显示。没有阻塞的工单可以并行。开发计划要求先交付某个结果时，先派发就绪的高优先级工单，再用剩余执行位派发其他就绪工单。

独立复核为每张新工单保留结论和原文证据。只有界面或数据层、无法单独演示的拆法，以及虚假依赖、同级顺序颠倒，均应在授权前拦截。源码复核区分无输出、输出超限、字段格式错误和引文无法核对。格式错误时用同一份资料重查一次。重查仍失败时，工作台显示工单及失败字段，保留其他工单的有效结论。结果、排序理由和前置说明进入授权卡及 Issue。依赖工单仍须等上游 PR 合并后启动。已授权的旧批次按原正文和回执续办。旧待授权草稿需要重新拆分和复核。

工单的每个验收编号只对应一项验证记录，多个操作可写在同一项验证步骤中。模型返回的编号或验证记录无法对应时，工作台在原计划和候选范围内提示具体工单并重试一次。修正结果重新通过完整校验后才进入复核，重复失败会留在授权前。

在固定设备接入样例中，本机 Astra 放行了可独立操作、顺序正确的两张工单，并分别拦截仅改界面、虚假依赖和颠倒同级顺序的反例。隔离工作台回读了[工单授权与优先顺序](acceptance/vertical-tickets/01-approval-order.jpg)和[逐单拦截依据](acceptance/vertical-tickets/02-blocked-dependency.jpg)。真实仓库建单与双机交付在 [#67](https://github.com/DikkooXie/souflow/issues/67) 验收。

隔离工作台使用固定规划样例验证[原对话重新规划入口](acceptance/replan/01-action.jpg)和[开发计划 v2 与历史 v1](acceptance/replan/02-history.jpg)。

新发出的澄清记录包含原请求版本、发起阶段和当时已确定的需求版本，有固定仓库提交时一并保留。只有拿到原会话确认的答复才会进入后续规划。产物记录本阶段收到的提问和答复编号，可在会话与审计中回查。旧卡仍可读取，缺失的历史版本信息保持为空。

### 查看和修订项目文档

在原对话打开「项目文档」，可预览 PRD 和开发计划的 Markdown，查看历史版本，或编辑当前源文并保存为新版。预览支持标题、列表、表格、代码块和链接，内嵌 HTML 按文本呈现，图片地址不会触发远端请求。

保存时核对正在编辑的版本。另一成员已保存同版时，需要查看新版后再应用未保存的草稿。修订 PRD 后，原开发计划仍可查看，并保留对原 PRD 的引用。核对新版 PRD 并保存相应开发计划后才可重新拆单和授权。既有工单草稿保留在历史中。

隔离工作台用设备接入样例验证了 [Markdown 编辑与预览](acceptance/markdown-docs/01-edit-preview.jpg)、[保存并重开后读取新版](acceptance/markdown-docs/02-version-readback.jpg)和[旧计划待修订](acceptance/markdown-docs/03-stale-plan.jpg)。双成员保存冲突与重启回读由 HTTP 集成测试覆盖。

### 从原对话查看交付复核

工作台发现关联 PR 后，分别启动两个只读 Codex 会话，固定 Issue 正文版本、PR 头提交、比较起点和已批准的计划。代码质量结论引用该提交的代码或测试差异。需求结论逐项引用对应验收条件，判为通过时必须引用与该编号对应的实际测试回执。隔离检查使用固定 TAP 报告格式，只保存已运行通过的验收测试名称。跳过和待办测试不算证据。

原对话的「交付复核」可展开两侧结论和引文。新 PR 提交进入新一轮复核，旧结果仍可回查。当前提交缺少验收回执时，界面保留阻塞或证据不足状态。复核可以为验收提供证据，GitHub 的 CI、评审、合并和成员验收按现有流程处理。关联修复工单与真实双机复验的进度见 [#70](https://github.com/DikkooXie/souflow/issues/70) 和 [#67](https://github.com/DikkooXie/souflow/issues/67)。

[隔离样例截图](acceptance/delivery-review/01-two-axis-history.jpg)展示代码质量拦截、需求项通过及旧提交历史的回读界面。样例的复核材料使用固定测试数据。

### 首版双机单账号试用

使用两台实体电脑和同一个已登录的 Codex 账号。选择同一个真实仓库里的两张不同工单，分别在各自机器的本地会话与独立 Git 工作区完成开发和测试，提交可追溯到对应 Issue 的 PR。至少验证一次通过 GitHub 的跨机交接：上游 PR 合并后，下游电脑从合并后的提交开始或继续其工单。保存两台电脑各自的执行或测试截图，以及关联 Issue、PR、提交和 CI，核对负责人和工单没有串单。此试用以各自机器本地启动执行，GitHub 承载协作和交接。

[B6 局域网双机实测与截图（PR #42）](https://github.com/DikkooXie/souflow/pull/42)记录 Mac 接入包、两台实体 Mac 在线、只读核验在断线后从 `1/3` 恢复到 `3/3`，以及单次领取。它提供设备接入和恢复的证据。后来用两台 Mac 和同一 Codex 账号实测了不同工单的开发，以及从上游合并提交开始的代码交接。[首版双机验收](acceptance/two-mac-code-handoff.md)。单机同账号多会话已有[实测证据](acceptance/session-account.md)。单机跨账号的[接入和测试记录](acceptance/codex-account-dispatch.md)作为以后多机多账号试验的参考。

## 编排长期开发计划

每个阶段都应交付一个当期能用的结果。决定先做哪项时，比较用户价值、依赖和实现成本。在其他条件相近时，优先做能替下一阶段省去实际工作的那一项。比如先让开发调度器接手 souflow 自身的开发工单，后续模块便可以直接沿用已验收的派发和交付流程。

| 规划时回答的问题 | 在计划中留下什么 |
| --- | --- |
| 这一阶段交付后，谁能用它完成什么？ | 一个具体场景、可观察的验收条件，以及要复用的已有能力和版本。 |
| 哪项后续工作会因此变容易？ | 指出下一张候选工单、它会调用的能力，以及可省去的手工步骤。把潜在复用收益标为预期，等到具体场景出现再提取共用接口。 |
| 怎样判断这次排序值得？ | 在下一阶段选一张真实工单使用上阶段的交付，关联工单、PR 和审计记录。与范围相近、验收标准相同的历史工单对照，并计入接入和维护成本。 |

复盘时先核对质量和预算，再看人工介入、返工、交付耗时和模型用量。把实际省下的步骤、增加的工作和适用条件写回项目知识库。缺少可比样本时保留观察，继续收集证据。下一轮规划用这些结果决定继续复用、调整接口，还是把精力转向更迫切的需求。

## 同一条需求经过各阶段的样子

| 产物 | 示例内容 |
| --- | --- |
| 成员原话 | “我想把筛过的工单导出给同事看。” 经追问，成员选 CSV，并确认导出顺序与页面一致。 |
| 结构化需求 REQ-1 v1 | 角色为项目成员，场景为在工单列表筛选后分享结果。AC-1 要求 CSV 只含命中且当前成员可见的工单；AC-2 要求行序与列表一致。示例中两项均由成员确认。 |
| PRD v1 | 引用 REQ-1 v1。用户在筛选结果页点击导出即可取得 CSV。列出 AC-1、AC-2，以及供审阅者对照的样例输入和期望输出。 |
| 开发计划 v1 | 引用 PRD v1。步骤 S1 打通筛选结果到 CSV 的导出并验证可见范围；S2 在 S1 基础上支持保留当前排序，以降序列表验收。 |
| 工单 | T1 对应 S1、AC-1：交付可演示的筛选导出，验证无权查看的行未被导出。T2 对应 S2、AC-2，依赖 T1：交付排序一致的导出，以样例逐行对照。两单均绑定计划 v1。 |

原型演示时，成员应能从 T2 点回 S2、PRD v1、REQ-1 v1 和“保留排序”的原始答复。若改为按创建时间导出，系统应能指出 AC-2、S2 和 T2 需要重新审阅，并保留旧版引用。

**最小验收场景。** 用“导出工单”发起访谈，先确认导出的范围，再生成带验收 ID 的方案与工单。以下反例应分别给出可定位的失败原因：

- 模型推荐“导出整个项目”，用户尚未回复；系统保留为待答。
- 两张工单互相依赖，或新拆分漏掉关键验收条件；拆分无法提交确认。
- 用户确认 v1 后修改为 v2；旧批准无法触发新版派单。
- 两个执行器同时领取同一张单；只产生一次有效尝试。
- 执行器报告完成但缺少验收证据；工单进入待补证或待审，人工可退回。

拆单中的纯结构规则可在仓库根目录用 Node 22.17+ 运行 `node --experimental-strip-types --test tests/ticket-plan.test.mts`。产品状态持久化、权限校验和外部派单由后续实现分别验收。
