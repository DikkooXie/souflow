# B4 本机任务持久化和断线恢复

使用 macOS、本机 Codex CLI 0.171.0-alpha.13、Node 22.17.1 和 Chromium。两个独立浏览器上下文分别登录实施成员和验收成员。规划阶段通过真实的本机 Codex App Server，使用回环端点提供固定模型响应，以便重复触发澄清。拆单使用固定结果。两张依赖代码工单由本机 Codex 登录的 GPT-6.2 Sol 在独立会话中生成补丁。

| 实测操作 | 观察结果 | 截图 |
| --- | --- | --- |
| 在一条需求等待澄清、另一条需求的 T1 补丁等待审批时强制终止工作台，再使用同一数据库启动 | 原需求、调研产物与工单批次保留。旧澄清卡失效，向原地址答复返回 409。原补丁审批卡及补丁摘要保留。 | [工作台重启后的对话](b4/02-after-workbench-restart.png) |
| 恢复原需求，再单独终止该轮的 App Server 进程 | 工作台继续服务，显示失效提问。再次继续时获得新的请求 ID，完成新卡后继续规划。调研阶段没有重跑。 | [单独断开 App Server 后的状态](b4/04-after-app-server-disconnect.png) |
| 使用两个成员身份处理恢复后的批次，再正常重启一次 | 实施成员审批补丁返回 403。验收成员批准 T1 后，实施成员继续派发，T2 引用同一 T1 产物及 SHA-256。再次重启后，验收成员通过已提交的原批次。未登录读取返回 401。 | [重启后完成最终验收](b4/05-restored-final-acceptance.png) |

工作台停止后，成对复制 SQLite 和产物目录，随后在原路径从备份恢复。回读同一批次的两位成员验收记录，并重新计算两个补丁的 SHA-256，均与数据库中的摘要一致。两次执行各有一个 Codex 会话。

自动化测试另覆盖存储写入失败时禁止发送答复、未获回执的答复进入待核对、重复恢复被拒、切换登录模式被拒，以及恢复后的补丁验收和版本校验。验证范围限于本机工作台和本机 App Server。
